# full-jdks-proj
a proj using all the jdk21 packages

## 启动方式

**方式一：在 IDEA 里直接运行（推荐日常开发）**

仓库已带运行配置 `.idea/runConfigurations/Frontier_Chronicle.xml`：

1. 打开项目后若右下角提示 Maven 项目，点 **Load/Reload**（或右键 `pom.xml` → *Add as Maven Project*），让 IDEA 识别 15 个 `fc-*` 模块；
2. 运行下拉框选 **Frontier Chronicle**，点绿色三角；
3. 也可直接右键 `fc-runtime/src/main/java/fc/runtime/Main.java` → *Run 'Main.main()'*。

> `Main` 会自动判断控制台编码：IDEA 控制台已是 UTF-8 则不动，Git Bash/重定向则切 UTF-8；关闭用 `-Dfc.stdout.utf8=false`。

**方式二：打包成单文件 jar**

```bash
# 打包（首次或改代码后）
JAVA_HOME=E:/jdks/ms-21.0.11 ~/.m2/wrapper/dists/apache-maven-3.9.16-bin/*/bin/mvn -q -pl fc-runtime -am package -DskipTests

# 进游戏
java -jar fc-runtime/target/frontier-chronicle.jar
```

开局照 `help` 里的「跑商开局」走：`market` → `trade buy food 100` → `sail 1 8` → `next 14` → `trade sell food 100` → `log`。

> 输入 `help` 可看到**全部命令**（11 条命令 + `chronicle`/`exit` 两个别名，共 13 项）。

> M1 起不再提供验收脚本（按用户要求），直接 IDEA Run 或跑 jar 即可。

## 版本变更迭代

### v0.3.0 2026-11-21 阶段五 M3：经济与贸易

1. **供需定价**：`PriceModel` 幂函数定价（库存低于目标即涨价，夹在 0.3×–5×），买价 ×1.05 / 卖价 ×0.95。

3. **组织收支**：`MarketSystemImpl` 阶段 9 发工资，地点没钱则欠薪 → 士气下降。
4. **玩家交易**：`market` / `trade buy|sell|quote`，支持**部分成交**；货物与信用点总量守恒。

6. 测试 35 个通过（M3 11 + M2 11 + M1 7 + fleet 6）。

# 项目任务：基于 Java SE 21 全量标准 API 的星际远征与自主世界模拟游戏

## 一、项目目标

设计并实现一个基于 **Java SE 21** 的完整命令行游戏。

游戏采用「星际远征 + 舰队经营 + 自主世界模拟」的形式。

玩家经营一支独立的星际远征舰队，在一个持续演化的未知星域中开展探索、贸易、科研、建设和外交活动。

玩家不仅需要管理自己的舰队、飞船、船员、资源和前哨站，还需要面对一个能够自主运行的星域世界。其他势力、星球、市场、船员和殖民地都具有一定的独立行为能力。

本项目有一个特殊且重要的工程目标：

**在保证应用真实、完整、合理的前提下，尽可能充分地使用 Java SE 21 规范定义的全部标准 API。**

这不是一个 API 演示程序，也不是一组独立 Demo 的集合。所有功能必须服务于同一个连贯的游戏世界。不得为了提高 API 覆盖率而引入没有实际意义的功能。

最终交付必须包含：
- 完整的游戏设计。
- 完整的系统架构。
- Java SE 21 标准 API 基准清单。
- API 使用覆盖审计报告。
- 可运行的完整源代码。
- 构建、运行和测试说明。

## 二、游戏方向

暂定项目名称：Frontier Chronicle（边境纪事）。

游戏类型：星际远征经营策略游戏，融合舰队管理、探索、贸易、科研、殖民和自主世界模拟。

### 2.1 游戏世界

玩家经营一支独立的星际远征组织，在一个尚未完全探索的星域中开展活动。

这个星域不是静态地图，而是一个持续演化的模拟世界。

世界至少具有以下概念：

**1. 星域与空间结构**
- 星域：由多个星系、星球、空间站和特殊地点组成。
- 星系：具有空间坐标、天体结构和航行连接关系。
- 星球：具有地形、环境、气候、资源、生态和开发潜力。
- 航线：连接不同地点，具有航行时间、危险程度和运输成本。
- 未知区域：包含尚未发现的地点、资源、遗迹和异常现象。

**2. 玩家远征组织**
- 组织：具有资金、声望、技术水平、发展状态和组织目标。
- 舰队：由多艘飞船组成，具有独立的航行、任务和维护状态。
- 飞船：具有类型、设备、能源、燃料、货舱、耐久度和功能定位。
- 前哨站：用于资源采集、补给、研究和区域控制。
- 殖民地：具有建筑、人口、生产、消费和发展状态。

**3. 船员与居民**
- 身份：姓名、年龄、职业、背景和所属组织。
- 属性：健康、精力、情绪、能力和其他状态。
- 技能：驾驶、工程、科研、医疗、贸易、探索等。
- 需求：食物、休息、安全、社交和其他生活需求。
- 工作：岗位、任务、工作效率和工作安排。
- 关系：友谊、冲突、信任、合作及其他社会关系。
- 经历：个人历史、参与事件、任务成果和成长记录。

船员和殖民地居民不能只是静态属性集合，应当具备一定的自主行为能力。

**4. 资源与经济**
- 资源：燃料、能源、食物、矿物、金属、材料、设备和其他商品。
- 生产：采矿、加工、农业、能源生产和制造。
- 消费：船员生活、飞船运行、建筑维护和科研活动。
- 贸易：商品价格、供需关系、运输成本和市场变化。
- 财务：资金收入、支出、债务、利润和组织经济状况。

**5. 势力与文明**
- 其他远征组织。
- 星际贸易集团。
- 独立殖民地。
- 地方政权。
- 未知文明或特殊势力。

不同势力应当具有自己的资源、目标、关系、经济活动和行为倾向。

**6. 环境与生态**
- 星球环境、地形、气候和自然资源。
- 昼夜、周期和环境变化。
- 植物、动物及其他生态系统。
- 自然灾害和特殊环境现象。
- 资源再生与环境承载能力。

**7. 事件与世界历史**
- 航行事件。
- 探索发现。
- 船员个人事件。
- 飞船故障。
- 资源危机。
- 贸易与经济变化。
- 势力冲突与外交事件。
- 殖民地发展事件。
- 自然灾害和环境变化。

重要事件应当记录发生时间、地点、参与者、原因、过程和结果，形成可以查询的世界历史。

星域模拟和殖民地模拟应当是同一套世界规则下的不同尺度，而不是两套互不相关的模拟器。这样船员、居民、资源、时间、事件和经济系统才能复用同一套基础机制，避免项目最终变成多个独立子游戏的拼接。

具体规模和复杂度由设计阶段确定，不必一次实现所有设想。

### 2.2 游戏运行方式

采用回合制或离散时间推进机制。

玩家不直接控制世界中的每一个角色，而是通过经营决策、任务指派和策略干预影响世界。

玩家可以：

- 查看星域地图和已知地点。
- 查看舰队、飞船和船员状态。
- 建造、购买、维修和升级飞船。
- 配置飞船设备和舰队编组。
- 招募船员并分配岗位。
- 管理资源、货物和资金。
- 规划航线和安排运输。
- 接受委托和执行远征任务。
- 探索未知星球和特殊地点。
- 建设前哨站和殖民地。
- 进行贸易和市场交易。
- 研究技术和解锁新能力。
- 与其他势力建立关系、开展外交或竞争。
- 处理突发事件。
- 查询舰队日志和世界历史。
- 保存和加载游戏。

每次推进时间时，世界应当自主结算：

- 飞船航行和任务进度。
- 舰队燃料、能源和物资消耗。
- 船员工作、休息和个人行为。
- 船员需求、状态和关系变化。
- 殖民地居民的生产、消费和生活活动。
- 前哨站和殖民地的运行。
- 资源生产、消耗和市场供需变化。
- 科研项目进度。
- 其他势力的经济、外交和扩张行为。
- 星球环境和生态变化。
- 随机事件和特殊事件。
- 探索队伍的行动与发现。
- 世界历史的更新。

时间推进不应只是简单地累加日期，而应当真正驱动游戏世界中的各个系统。

玩家没有直接参与的活动也可以继续发生，但需要遵守统一的世界规则和时间逻辑。

### 2.3 核心玩法循环

游戏应当形成明确、持续且相互关联的经营与探索循环：

1. 获取信息：了解星域状况、市场、任务和势力动态。
2. 制定计划：确定探索、贸易、建设或科研目标。
3. 配置资源：安排舰队、船员、飞船、燃料和物资。
4. 执行行动：航行、探索、运输、交易或建设。
5. 世界演化：其他角色和势力继续自主活动。
6. 结果结算：获得收益、消耗资源、产生事件和新的局势。
7. 调整策略：根据世界变化制定下一阶段计划。

玩家的行动应当对世界状态产生真实影响，世界的自主演化也应当反过来影响玩家的决策。

### 2.4 命令行交互

使用纯文本命令行作为主要交互界面。

需要提供：

- 清晰的命令体系。
- 帮助和命令提示。
- 星域及地点查询。
- 舰队和飞船状态面板。
- 船员信息和管理。
- 资源、货物和市场查询。
- 任务和事件报告。
- 势力关系查询。
- 科研进度查询。
- 航行和探索结果。
- 世界历史查询。
- 存档管理。
- 输入错误处理。

命令设计应当围绕游戏中的真实操作组织，而不是围绕 Java API 的分类组织。

不要求使用第三方终端 UI 框架。优先使用 Java SE 21 标准 API 实现。

### 2.5 初始规模与复杂度控制

不得一开始就尝试模拟整个银河系。

设计阶段应当根据完整游戏玩法、API 规模和工程复杂度确定合理的初始世界规模。

可以将以下内容作为初始规模的参考，而非必须遵守的硬性指标：

- 一个可探索星域。
- 约 10～20 个具有不同特征的地点。
- 3～5 个具有独立行为的其他势力。
- 一支玩家远征舰队。
- 数种具有不同功能定位的飞船。
- 数十名具有个体状态的船员。
- 一个可建设和管理的前哨站或殖民地。
- 一套完整的航行、贸易、探索和时间推进系统。

优先保证有限规模下各个系统能够真实运转、相互影响，并形成可持续的游戏体验。

在核心玩法得到验证之后，再逐步扩展世界规模和系统复杂度。

不得为了容纳更多 API 而无节制地扩大游戏世界。

## 三、Java SE 21 API 范围

这是本项目最重要的技术约束。

### 3.1 权威来源

以官方 Java SE 21 API Specification 为唯一的规范公开 API 基准。

https://docs.oracle.com/en/java/javase/21/docs/api/

不能仅凭包名前缀判断某个 API 是否属于 Java SE。

应当依据 Java SE 21 规范中的模块、包和公开类型定义建立完整清单。

### 3.2 纳入范围

纳入 Java SE 21 规范正式定义的公开 API，包括：
- public class。
- abstract class。
- interface。
- enum。
- annotation。
- record。
- sealed class 和 sealed interface。
- 规范列出的其他公开类型。

嵌套公开类型独立计数。

以 Java SE 21 API Specification 中的公开类型为准，不通过扫描 JDK 实现类猜测规范全集。

### 3.3 排除范围

以下内容不计入正式标准 API 覆盖率：
- Java EE / Jakarta EE API。
- Java SE 21 规范之外的 JDK 专有 API。
- `jdk.internal.*`、`sun.*` 等非规范内部实现 API。
- Java SE 21 Preview API。
- Incubator API。

Preview 和 Incubator API 应当单独记录，不得混入正式覆盖率分母。

需要特别注意：不能因为一个类型位于标准包中，就认为它必然是正式 API。例如某些预览类型可能位于标准包内。

### 3.4 废弃 API

`@Deprecated` 类型仍然属于 Java SE 21 正式 API，必须保留在统计分母中。

`@Deprecated(forRemoval=true)` 同样保留，并单独标记。

不得因为 API 已废弃、使用不推荐或预计移除，就直接从清单中删除。

### 3.5 模块与包

建立以下层次的基准清单：

Java SE 21 标准模块 → 标准包 → 规范公开类型。

注意：
- `java.se` 聚合模块不能造成重复统计。
- 模块被 requires 不代表覆盖其所有包。
- 使用某个包中的一个类型不代表覆盖该包中的全部类型。
- 父包被使用不代表子包被覆盖。
- 以规范中的包归属为准。

## 四、API 覆盖统计模型

必须分别统计以下三个指标。

### 4.1 包级覆盖率

一个最小公开 API 包路径中，至少有一个类型被有效使用，即视为该包被覆盖。

\[
包级覆盖率 =
\frac{至少使用一个类型的包数量}{纳入统计的包总数}
\]

### 4.2 类型级覆盖率

每个纳入统计的公开 API 类型都需要被有效使用。

\[
类型级覆盖率 =
\frac{有效使用的公开 API 类型数量}{纳入统计的公开 API 类型总数}
\]

### 4.3 完整包覆盖率

一个包下全部纳入统计的公开 API 类型都被有效使用，才算完整覆盖该包。

\[
完整包覆盖率 =
\frac{全部类型均被有效使用的包数量}{纳入统计的包总数}
\]

三个指标必须独立展示，不得合并成一个笼统的覆盖率。

### 4.4 有效使用定义

只有应用代码中存在明确、可追溯、对游戏功能产生实际贡献的主动使用，才计入覆盖。

以下不计入：
- 仅 import。
- 注释中提及。
- 无意义调用。
- 反射加载后直接丢弃。
- 死代码。
- 仅测试代码使用，而生产应用没有使用。
- 其他 API 在内部间接调用该类型。
- 仅因为继承关系而自动获得的覆盖。

例如，继承某个抽象类，不代表其父接口及其他祖先类型都自动获得覆盖。必须有直接、明确、可追溯的应用使用证据。

以下形式可以计入，但必须有实际功能贡献：
- 显式类型声明。
- 对象创建。
- 方法调用。
- 接口实现。
- 类型继承。
- 注解的编译期语义。
- 反射。
- ServiceLoader。
- 其他合理的动态使用。

泛型参数化不重复计数。同一个类型在多个位置使用只计一次。

### 4.5 类型级与成员级区分

核心统计单位为类型。

不要求每个类型的所有方法、构造器、字段和重载都被使用。

成员级使用情况可以附加记录，但不得与类型级覆盖率混淆。

### 4.6 环境和运行条件

固定一个 JDK 21 发行版及具体版本作为实际运行环境。

规范全集必须以 Java SE 21 规范为准，不能因为特定 JDK 发行版缺少某个可选 Provider、硬件或环境能力，就从统计分母中删除相应规范 API。

区分：
- 规范 API 是否存在。
- 运行环境是否提供对应服务。
- 当前游戏是否具备使用条件。

## 五、设计原则

### 5.1 游戏优先

游戏必须是一个真正的应用，而不是 API 集合。

首先建立完整的游戏世界、规则和核心循环，再寻找合适的标准 API。

不得采用以下做法：
- 为每个 API 单独创建一个无关的 Demo。
- 建立没有游戏意义的 API 展示菜单。
- 为覆盖率强行增加功能。
- 在业务代码中插入无意义调用。
- 为了使用某个 API 而破坏原有架构。

### 5.2 合理性优先

每个 API 的使用都需要说明：
- 它解决了什么实际问题？
- 为什么选择它？
- 是否存在更自然的 Java SE 标准 API？
- 使用它是否增加了不必要的复杂度？
- 它是否真正融入了游戏系统？

### 5.3 保留无法覆盖项

并非所有 Java SE API 都适合本项目。

对于无法合理使用的 API，必须：
- 保留在完整基准清单中。
- 记录未覆盖状态。
- 给出具体原因。
- 说明属于业务无关、环境限制、特殊用途还是其他原因。

不得为了获得漂亮的覆盖率而篡改统计分母。

## 六、实施流程

必须分阶段工作，不得跳过设计和审计直接开始大规模编码。

### 阶段一：规范全集盘点

1. 获取并分析官方 Java SE 21 API Specification。
2. 建立模块、包、公开类型的完整清单。
3. 标记废弃、待移除、预览和孵化状态。
4. 统计模块数量、包数量、公开类型数量。
5. 记录数据来源及版本。
6. 检查清单是否存在遗漏和重复。

产出：
- `api-inventory.md`
- 结构化的 API 基准清单。
- 基准统计报告。

### 阶段二：游戏整体设计

在完整理解 API 规模之后，进行游戏设计。

首先确保星际远征游戏本身具有完整、连贯、有趣的玩法，再考虑后续 API 映射。

至少需要设计：

- 星域与空间结构系统。
- 舰队与飞船管理系统。
- 船员自主行为模拟系统。
- 殖民地与前哨站经营系统。
- 时间与回合推进系统。
- 资源生产、消耗和贸易系统。
- 航行、运输与物流系统。
- 地图与探索系统。
- 科研与技术发展系统。
- 势力、外交与关系系统。
- 事件与任务系统。
- 世界历史与日志系统。
- 命令行交互系统。
- 存档与加载系统。
- 游戏配置系统。
- 测试与验证系统。

需要重点说明：

1. 玩家长期追求的目标是什么？
2. 游戏的核心决策是什么？
3. 不同系统之间如何相互影响？
4. 船员、殖民地居民和其他势力如何自主行动？
5. 世界如何在时间推进时持续演化？
6. 玩家行动如何改变世界状态？
7. 如何避免世界模拟沦为大量互不关联的数值结算？
8. 如何控制初期规模，同时保留后续扩展能力？
9. 如何确保纯命令行交互仍然具有良好的可玩性？

需要给出：

- 游戏完整玩法说明。
- 核心循环。
- 世界观和初始背景。
- 游戏目标与发展阶段。
- 系统关系图。
- 核心数据模型。
- 模块划分。
- 时间推进与模拟结算机制。
- 关键技术决策。
- 初始世界规模。
- 预计实现阶段。

注意：本阶段只完成游戏整体设计，不要提前进行逐个 Java SE API 类型的功能映射。API 映射属于阶段三。

### 阶段三：API 与游戏功能映射

建立完整映射表。

每个 API 类型必须具有以下状态之一：
- Planned：计划使用。
- Implemented：已实现有效使用。
- Verified：已验证有效使用。
- Excluded：经过论证后不使用。
- Pending：尚未确定。

每个类型还应记录：
- 所属模块。
- 所属包。
- 类型名称。
- 是否废弃。
- 是否待移除。
- 计划使用的游戏系统。
- 具体使用场景。
- 预期代码位置。
- 实际使用证据。
- 未覆盖原因。

不能只列出热门 API。必须保留全部纳入统计的类型。

### 阶段四：分批实现

按照合理的工程顺序逐步实现游戏。

每个阶段都必须：
1. 明确本阶段的游戏功能。
2. 明确涉及的 API。
3. 完成设计和实现。
4. 编写测试。
5. 运行验证。
6. 更新 API 覆盖清单。
7. 检查是否引入无意义的 API 使用。

游戏必须始终保持可构建、可运行。

### 阶段五：最终审计

最终审计必须基于完整源码，而不是开发者自述。

检查：
- 每个类型是否真正被使用。
- 使用是否有实际功能贡献。
- 是否存在无意义调用。
- 是否有死代码。
- 是否将测试代码误算为生产覆盖。
- 是否存在重复统计。
- 是否错误地把继承或间接调用视为覆盖。
- 是否遗漏规范公开类型。

最终报告必须包含：
- 包级覆盖率。
- 类型级覆盖率。
- 完整包覆盖率。
- 各模块覆盖情况。
- 各包覆盖情况。
- 已覆盖类型清单。
- 未覆盖类型清单。
- 合理排除项及其理由。
- 证据不足的项目。
- 审计方法与复现步骤。

## 七、工程约束

- 使用 Java 21。
- 不引入第三方运行时或编译依赖。
- 优先使用 Java SE 21 标准 API。
- 可以使用 Maven 或 Gradle 作为构建工具，但必须说明构建工具与应用运行依赖的边界。
- 不得依赖 Java SE 21 之后才出现的 API。
- 不使用 Preview API 作为正式实现的一部分。
- 代码结构必须清晰，避免为了覆盖率形成高度耦合的巨型类。
- 必须提供自动化测试。
- 必须提供完整的构建和运行说明。

## 八、最终交付标准

最终项目应当同时满足：

1. 游戏本身是完整、连贯、可玩的应用。
2. 世界具有持续演化能力，而不是一组静态命令。
3. 玩家操作能够真实影响世界状态。
4. 居民和事件具有一定的自主行为。
5. 能够保存和恢复游戏。
6. 不依赖第三方运行时或编译依赖。
7. 使用 Java SE 21 标准 API。
8. API 覆盖率具有明确、可复现的统计依据。
9. 所有无法合理覆盖的类型都有记录。
10. 不以牺牲游戏质量换取覆盖率。

**最终目标不是得到一个 API 使用数量最多的程序，而是得到一个在真实游戏设计中尽可能充分使用 Java SE 21 标准 API 的完整应用。**

## 九、Agent 执行要求

首先只执行阶段一和阶段二，不要直接开始编码。

先完成规范全集盘点，再根据实际 API 规模和游戏设计提出具体实施方案。

在每个阶段结束时提交：
- 已完成内容。
- 关键决策及理由。
- 尚未解决的问题。
- 下一阶段计划。
- 与 API 覆盖目标相关的风险。

遇到规范边界、API 状态、类型归属等问题时，必须回到官方 Java SE 21 文档核验，不得根据记忆猜测。

对于无法确认的内容，明确标记为待核验，不得伪造确定结论。

在得到用户对阶段性设计的确认之前，不得擅自进入下一阶段。
