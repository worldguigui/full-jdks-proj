# 架构

Frontier Chronicle（边境纪事）是一个纯命令行、回合制的星际远征模拟游戏。本文件说明各模块如何协作、世界状态由谁拥有、一次回合如何结算，以及哪些不变量不可破坏。

## 1. 设计目标

1. **一个世界，一种规则**：星域、舰队与殖民地不是三个子游戏，而是同一套位置、主体、库存、生产、事件与时间机制在不同尺度上的实例。
2. **世界自己会动**：船员、居民与势力都是带需求与目标的自主主体；玩家推进一天，世界沿同一条时间轴结算。
3. **历史可查询**：所有重要结果写入同一部编年史，可以按时间与类型检索。
4. **确定性可重放**：同一种子与同一操作序列必须得到同一状态哈希。
5. **零第三方依赖**：编译期与运行期只使用 Java SE 21 正式 API，不使用 Preview/Incubator 特性。

## 2. 统一世界模型

五个抽象承载全部世界规则，定义都在 `fc-world`：

| 抽象 | 职责 |
|---|---|
| `Location`（sealed） | 可容纳主体与库存的空间节点；`Ship` 是移动的 `Location`，`Colony`/`Facility` 与恒星系、行星、轨道站、异常点并列 |
| `Link`（sealed） | 两个 `Location` 之间的通行边，带天数、风险与成本；航线按无向边参与寻路 |
| `Agent` | 有角色（`CREW`/`RESIDENT`/`ENVOY`）、需求、性格与技能的行为主体；角色不是子类 |
| `Stock` + `ResourceLedger` | 货物账本。`ResourceLedger` 是权威数据，`Stock` 是某地点的不可变分区快照 |
| `WorkUnit` + `Recipe` | 输入资源、工作天数、产出资源的统一生产单位 |

`Location`、`Link`、`GameEvent` 的 sealed 根与全部 permitted 类型必须同处 `fc-world`（JPMS/JLS 约束）。领域模块只提供服务与结算行为，不新增 sealed 子类型。两个 `non-sealed` 扩展口 `ExtensionLocation`、`ExtensionEvent` 保留给后续 Mod 机制，M0–M3 不实现加载器。

### 2.1 状态所有权

`WorldState` 是唯一的可变世界根，持有：

- 地点图（节点按 id 排序）、主体表（按 id 排序）；
- 货物账本与财务账本；
- 势力、关系矩阵、声望、殖民地；
- 在途运输、补给线、工作单元、待决决策；
- 风险修正、停产窗口、价格冲击；
- 当前 `Stardate` 与编年史接口。

`GameLoop` 与 `TickPipeline` 位于 `fc-sim`，持有对 `WorldState` 的引用并驱动结算；`Chronicle` 只留接口在 `fc-world`，实现在 `fc-history`。这样 `fc-world` 保持最底层、无业务依赖。

### 2.2 货物与信用点

- 货物共 11 种：燃料、能源、食物、水、矿物、金属、材料、设备、药品、奢侈品、科研数据。
- 信用点不是货物，只存在于 `MoneyLedger` 的账户中，不允许写进 `Stock`。
- 库存不允许为负；`consume` 在不足时失败，`tryConsume` 返回 `false` 且不改变状态。
- 唯一允许增加货物总量的操作是生产（包括环境再生）；唯一允许减少总量的操作是消耗。转运、补给线与运输在两端记账，总量不变，并由账本守恒断言兜底。

## 3. 时间与回合

- 1 tick = 1 星历日；`Stardate` 是世界时间的唯一来源。
- 游戏时间（星历）决定状态、编年史与重放；系统时钟只用于日志与监控，绝不进入世界状态。
- `next <n>` 逐日执行管线。出现待决决策时立即停止推进，直到玩家用 `decide` 处理完毕。

### 3.1 十二阶段 Tick 管线

| # | 阶段 | 主要职责 |
|---|---|---|
| 1 | 时间推进 | `Stardate++`，采样天气/环境，清理到期的价格冲击与停产窗口 |
| 2 | 环境与生态 | 地点自然产出（处于停产窗口时跳过）、殖民地维护 |
| 3 | 势力 AI | 势力采购其优先货物（受资金与目标库存约束） |
| 4 | 主体感知 | 刷新饥饿、疲劳、士气 |
| 5 | 主体决策 | 进食、休息、工作、觅食迁徙、拒绝指令 |
| 6 | 生产与工作 | 配方开工、工作单元推进、完工产出 |
| 7 | 航行与物流 | 舰船航程推进、在途运输抵达、补给线发车 |
| 8 | 消耗与维护 | 口粮消耗、贷款利息 |
| 9 | 市场与财务 | 工资、组织收支、市场结算 |
| 10 | 事件引擎 | 离子风暴生成与传播、价格冲击写入、待决决策 |
| 11 | 编年史落库 | 将本 tick 的有序事件写入编年史 |
| 12 | 报告聚合 | 生成回合报告行 |

阶段顺序固定，下游阶段读取上游刚写入的真实状态。领域系统通过 `fc-sim` 中的 SPI（`ProductionSystem`、`MarketSystem`、`FactionSystem`、`ColonySystem`）注入，避免 `fc-sim` 反向依赖领域模块。

### 3.2 确定性

- 世界内所有遍历使用有序结构或显式排序：地点按 id、主体按 id、舰船按 id、运输按 id、编年史按入队顺序。
- 随机数来自 `RngStreams` 按子系统派生的独立流（天气、事件、主体、市场、势力）；同种子重放不受其他子系统调用次数影响。
- tick 内事件进入有序 `EventQueue`，只在阶段 11 落库。
- `EventBus`（`java.util.concurrent.Flow`）只在 tick 结束后广播，供报告/遥测读取，不参与状态写入。
- `StateHasher` 对可观察状态按确定顺序序列化后求 SHA-256，作为重放验收依据。

## 4. 模块与依赖

```
fc-world ← fc-config ← fc-sim ← 领域模块（fleet/colony/economy/diplomacy/…）
                                   ↑
                             fc-cli / fc-runtime
```

| 模块 | 当前职责 | 状态 |
|---|---|---|
| `fc-world` | 统一世界模型、账本、事件类型、`WorldState`、`Chronicle` 接口、时间 | 已实现 |
| `fc-config` | 世界配置模型、XML/XSD 校验装载、世界装配输入 | 已实现 |
| `fc-sim` | Tick 管线、游戏循环、主体决策、事件队列/总线、RNG、状态哈希、SPI | 已实现 |
| `fc-fleet` | 航路寻路、启航与燃料校验 | 已实现 |
| `fc-economy` | 配方生产、供需定价、市场结算、玩家交易 | 已实现 |
| `fc-colony` | 殖民地升级、补给线管理 | 已实现 |
| `fc-diplomacy` | 势力采购与关系数据；外交动作未实现 | 已实现（采购） |
| `fc-history` | 内存编年史实现 | 已实现（内存版） |
| `fc-cli` | 命令解析、星图、面板与报告 | 已实现 |
| `fc-runtime` | 装配、启动横幅、REPL、单文件 jar | 已实现 |
| `fc-testkit` | 注解 + 反射的零依赖测试框架 | 已实现 |
| `fc-science` | 科研系统 | 骨架（M4 起实现） |
| `fc-persist` | 存档、偏好、本地化 | 骨架（M5 起实现） |
| `fc-extensions` | Mod、运行时编译、JMX/音频/联网等外围能力 | 骨架（M5 起实现） |
| `fc-audit` | API 覆盖审计 | 骨架（M6 起实现） |

依赖方向：`fc-world ← fc-config ← fc-sim / 领域模块 ← fc-cli / fc-runtime`。领域模块之间不互相依赖；跨域协作通过 `WorldState` 与 `GameEvent`。`fc-testkit` 只作为测试作用域依赖。

## 5. 运行时装配

`fc-runtime` 的 `RuntimeSession` 完成一条固定启动链：

1. 读取 `world/default-world.xml`（或 `--world <path>`），经 XSD 与语义校验生成 `WorldDefinition`；
2. `WorldAssembler` 装配地点图、舰船、主体、货物/财务账本、势力、殖民地与初始关系；
3. 以配置的经济参数构造 `Economy` 与各领域系统，注入 `TickPipeline.m3`；
4. 创建 `GameLoop`、`Cli` 与 `EventBus`，打印启动横幅并进入 REPL。

所有世界数据来自配置，核心代码不硬编码地点、舰船、货物或配方。`RuntimeSession` 与 REPL 分离，使集成测试可以复用完全相同的装配路径。

## 6. 设计上尚未解决的决策

以下问题在既有设计材料中没有给出可执行结论，代码中的取值属于暂定实现，不应视为已确认设计：

1. **技能模型**：设计提出 `SkillSet`（驾驶/工程/科研/医疗/贸易/探索），当前 `Agent` 只有一个 `skill` 整数且生产结算不读取技能。技能如何进入生产、航行与科研公式尚未定案。
2. **初始殖民地数量**：设计规模写「前哨站/殖民地 1 个」，默认世界另有 2 个非玩家殖民地作为势力据点。非玩家殖民地的数量与初始规模口径需要统一。
3. **D1「知名」门槛**：设计要求与某个势力达到「知名」，但没有给出声望阈值；当前 `goals` 以声望 ≥ 20 作为暂定判据。
4. **风暴与事件参数**：事件概率、强度、传播上限、援助代价当前在代码中固定；设计要求事件由配置定义，配置化的字段与格式尚未确定。
5. **航行风险结算**：`Link.risk` 与风暴风险修正已写入状态，但尚未进入航程事故结算。风险如何转成延误、损伤或货损需要设计。
6. **选址与生产设施**：设计要求 `Facility` 挂载配方；当前配方按地点配置，没有独立的设施层级与岗位模型。
7. **税收**：设计要求价格受势力税率影响；当前 `PriceModel` 只含基础价、供需与冲击，税种、税率与征收对象未定案。
8. **工资循环**：工资从地点账户支付给家庭账户，家庭账户的消费回流路径尚未设计；当前家庭账户只累积。
9. **定价精度**：设计规定经济链使用 `BigDecimal`，但幂函数定价只能经 `double` 计算后转回，极端库存下的数值误差未验收。
10. **舰船与船员承载**：设计要求飞船有类型、货舱、耐久与船员铺位；当前舰船没有容量、耐久与船员隶属关系，船员不随船移动。
11. **tick 内事件消费**：当前事件由产生阶段直接修改状态，队列承担排序与落库；设计中的“系统消费事件后继续结算”缺少优先级与重入规则，M0–M3 不引入事件驱动结算。
12. **贷款交互**：财务账本支持借款与利息，CLI 只有 `finance` 查看，没有借款/还款命令；还款规则未定案。
