## 二、关键决策及理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | **统一世界规则**：五个统一抽象（`Location` / `Link` / `Agent` / `Stock+ResourceLedger` / `WorkUnit`）+ 单一 `Stardate` + 单一 `Chronicle`；星域与殖民地只是同一套类型的不同实例参数 | 任务书明确要求「同一套世界规则下的不同尺度，而不是两套互不相关的模拟器」。把复用**固化在类型系统层面**（`Colony`/`Facility` 与 `StarSystem` 同为 `Location` 子类型；`Crew`/`Resident`/`Envoy` 同为 `Agent` 实例），比口头约定更可靠 |
| 2 | 旧设计稿整体作废、不修补 | 新任务书的世界观、系统清单、核心循环、9 个重点问题均不同，局部改写会产生「两套设计缝合」；直接重写成本更低、一致性更好 |
| 3 | 初始规模严格收敛（1 星域 / 16 地点 / 4 势力 / 3→8 船 / 36 船员 / 1 殖民地 / 12 资源） | 任务书 §2.5 要求「不得一开始就模拟整个银河系」「不得为容纳更多 API 无节制扩大世界」；该规模足以跑通全部 16 系统的相互作用 |
| 4 | 配置驱动 + 未知地点惰性生成 | 扩展能力来自数据而非代码；潜在世界规模增长不影响存档体积与回合耗时 |
| 5 | 双终局（归途 / 扎根）+ D0–D4 发展阶段 | 回答「玩家长期追求什么」，并让长期资源投向形成策略分歧，而非结尾弹窗 |
| 6 | 用虚拟线程 + 固定顺序汇合实现并发，**不使用** `StructuredTaskScope`/`ScopedValue`/FFM/字符串模板 | 这些在 JDK 21 仍是 Preview，任务书 §7 禁止；阶段一已将 38 个类型排除分母 |
| 7 | 命令体系围绕游戏动作组织，信息三层下钻 + 叙事化回合报告 | 任务书 §2.4 硬要求；纯 CLI 的可玩性靠信息设计而非额外 UI 框架 |
| 8 | 事件连锁因果 + 统一规则一致性测试 | 直接回应「避免世界模拟沦为大量互不关联的数值结算」；并把该约束变成自动化测试（§16-2） |
| 9 | 覆盖率分母采用 3836 / 176（任务书 §3.3 派生），清单边界保持 3874 / 177 | 尊重用户冻结数字，同时忠实任务书；差异给出规范原因，不粉饰、不静默改数 |

## 五、与 API 覆盖目标相关的风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `java.desktop` GUI 主体（约 1100+ 类型）无 CLI 场景 | 类型级覆盖率上限约 50–60% | 如实记录 `Excluded` + 理由，不粉饰分母；包级目标仍 ≥85% |
| 38 个 Preview 类型全部禁用 | 现代并发/FFM 覆盖缺失 | 用正式 API 等价实现；单独登记，不入分母 |
| 无头/外设差异 | 个别类型环境依赖 | 能力探测 + 优雅降级；原因码 = 环境限制 |
| 自研 JDBC / ScriptEngine / JNDI / 运行时编译工作量 | M5 延期 | 只读/最小语义，砍范围不砍合理性 |
| 虚拟线程 + 共享账本的并发与确定性 | 死锁/竞态/重放失效 | 固定顺序汇合、领域锁规约、有序集合、压测入 CI |
| **方向变更导致的返工风险** | 已完成的设计/映射需随任务书同步 | 本轮已将旧稿作废并整体重写；后续以 README Prompt 为唯一方向源，每次阶段提交前核对 |
| 统一世界规则被后续扩展破坏 | 退化为多个子游戏拼接 | §16-2 一致性测试 + 代码评审红线；扩展只加配置不加重模拟器 |
| 覆盖率诱惑（塞无意义调用） | 违反任务书 §5 | 阶段五静态审计 + 人工复核；宁可低分不造假 |
